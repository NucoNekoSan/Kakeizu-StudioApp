# セキュリティ評価（ブラウザ内完結版）

基準: OWASP ASVS 5.0 Level 2、OWASP Web Security Testing Guide

v2 系（PHP + SQLite のサーバー保存）からローカルファースト構成へ移行したことで、脅威モデルが根本的に変わった。本書は v3 以降の構成を対象とする。v2 系の診断記録は `legacy/php-server` ブランチを参照。

## 構成と前提

- 配信は静的ホスティングのみ。アプリケーションサーバーとデータベースを持たない
- 利用者のデータは端末の IndexedDB にのみ保存され、外部へ送信されない
- 認証は行わない（預かるデータが無いため）
- 想定利用者に福祉・医療の対人援助職と士業が含まれ、入力内容に要配慮個人情報が含まれ得る

## 消滅した脅威

サーバーを持たないことで、次は構造的に発生しない。

| v2 系の脅威                        | v3 での扱い                          |
| ---------------------------------- | ------------------------------------ |
| 認証情報の窃取、総当たり           | 認証が存在しない                     |
| セッション固定、CSRF               | サーバーへの状態変更要求が存在しない |
| SQL インジェクション               | データベースサーバーが存在しない     |
| 利用者間のデータ混線               | 1 端末 1 利用者。横断する経路が無い  |
| サーバー側の情報漏えい             | 提供者がデータを保持しない           |
| 委託先（ホスティング）からの漏えい | 静的ファイルのみを預ける             |

## 現在の脅威と対策

脅威は次の 4 軸に整理される。

### 1. 端末内のデータ残留

共有 PC でログアウトに相当する操作が無いため、前の利用者のデータが次の利用者から見える。

- 起動時に保存方法を選ばせる。「今回だけ使う」を選ぶと DocumentStore をインメモリ実装に差し替え、IndexedDB へ一切書き込まない（`src/storage/storageMode.ts`, `src/storage/localApi.ts`）
- 一時利用モードでは画面上部に常時バッジを表示し、閉じる・再読み込みの操作を引き止める。メモリ上にしか保持しないため再読み込みでも失われる点を、バッジと選択画面の双方に明記している
- 設定画面に「この端末のデータをすべて削除」を用意。IndexedDB のデータベースごと削除し、`kakeizu:` 接頭辞の localStorage（同居データの旧キーを含む）も消す
- 確認ダイアログの中から直接書き出せるようにし、消す前の退避を促す

残存リスク: ブラウザのプロファイル自体が共有されている場合、アプリ側の対策だけでは不十分。ゲストモードやプライベートウィンドウの利用を案内している。

### 2. 出力ファイルの管理

書き出した PNG と JSON はアプリの管理外に出る。ここが最も現実的な漏えい経路。

- JSON バックアップは任意のパスフレーズで AES-GCM 暗号化できる（PBKDF2-SHA256、反復 600,000 回、ランダム salt/IV。`src/storage/crypto.ts`）
- パスフレーズ紛失時に復元できないことを、書き出し前にチェックボックスで確認させる
- PNG 書き出しの直前に、氏名やメモがそのまま含まれる旨を表示
- 第三者の情報を含む場合、個人のクラウドストレージへの保存を避けるよう案内

暗号化を IndexedDB 全体へ広げていない理由は [architecture-decisions.md](architecture-decisions.md) に記録。要点は、鍵をメモリに持つ以上 XSS が成立した時点で鍵ごと奪われるため XSS 対策にならないこと。

### 3. XSS による端末内データの読み出し

XSS が成立すると IndexedDB の内容を読み出せる。ここが最大の技術的脅威。

- CSP を多層で適用（`public/_headers` と `vite.config.ts` の開発サーバー）。`script-src 'self'`、`object-src 'none'`、`frame-ancestors 'none'`、`base-uri 'self'`
- 外部スクリプト、外部フォント、解析タグ、CDN を一切使わない。自オリジン以外への通信が発生しない
- Service Worker の登録スクリプトを自動注入させず、インラインスクリプトを持たない
- `dangerouslySetInnerHTML` を使用していない
- 上記の回帰を `src/__tests__/delivery.test.ts` が静的に検知する

残存リスク: `style-src 'unsafe-inline'` は React Flow と既存のインラインスタイルのため維持している。スタイル経由の情報流出は `connect-src 'self'` と `img-src` の制限により実効性が低いが、将来 CSS-in-JS を廃止できた時点で nonce 方式を検討する。

### 4. データの喪失

端末内保存では、端末故障・ブラウザのサイトデータ削除・OS 再インストールで全消失する。可用性の観点ではこれが最大のリスク。

- JSON によるバックアップと復元を標準機能として提供
- 最終書き出し日時を記録し、未実施または 7 日以上経過で一覧に警告を表示
- 「端末に保存する」選択時に `navigator.storage.persist()` を要求し、ブラウザの自動削除の対象から外すよう試みる
- 復元時、未知のスキーマ版のファイルは部分的に読まずに拒否する（見えない欠損を避けるため）
- 読み込めない保存データは黙って空に落とさず、復元を促すエラーとして通知する

残存リスク: `persist()` は要求であって保証ではない。バックアップ導線を UI 上で強く出すことが実質的な対策になっている。

## 自動確認

- 型検査、ESLint、Vitest（145 件）
- 配信設定の回帰テスト: 外部参照の混入、CSP の緩和、Service Worker の長期キャッシュを検知
- 暗号化の往復、誤ったパスフレーズと改ざんの拒否
- バックアップの往復、未知バージョンの拒否、未知フィールドの保持

## 実ブラウザでの確認

Chromium で次を確認している。

- Service Worker の有効化、manifest とアイコンの取得
- オフラインでの再読込・一覧表示・新規作成
- CSP 違反およびコンソールエラーがゼロであること
- **自オリジン以外への通信がゼロであること**

## 運用上の事項

- HTTPS の強制と HSTS はホスティング側（Cloudflare）で設定する。手順は [deployment.md](deployment.md)
- アクセス解析・エラー監視は導入しない。導入すると改正電気通信事業法の外部送信規律の対象となり、「外部送信ゼロ」という説明が使えなくなる
- 依存ライブラリの脆弱性監査を定期的に実施する
- 本番での能動的侵入試験は実施していない。実施する場合は書面の許可、対象範囲、停止条件を別途定める
