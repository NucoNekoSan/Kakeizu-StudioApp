# アーキテクチャ決定記録

## ADR-001: 利用者データをサーバーに保存しない（ローカルファースト）

**状態**: 採用（v3.0.0）

**背景**

一般公開にあたり、想定利用者に福祉・医療の対人援助職と士業が含まれる。この層が利用する場合、ノードのメモ欄に支援対象者の病歴・障害・被支援歴が入り得る。これは個人情報保護法上の要配慮個人情報にあたり、取得に本人同意が必要で、オプトアウトによる第三者提供ができない最も重い区分となる。

サーバーに保存する構成では、提供者が次をすべて負う。

- 安全管理措置（組織的・人的・物理的・技術的）
- 漏えい等が発生した場合の個人情報保護委員会への報告と本人通知
- 開示・訂正・利用停止請求への対応体制
- ホスティング事業者に対する委託先監督

個人開発で恒久的に負える水準を超える。

**決定**

利用者のデータはブラウザの IndexedDB にのみ保存し、サーバーへ送信しない。認証も行わない。配信は静的ホスティング（Cloudflare Pages）のみとする。

**結果**

- 上記の法的責務の大半が発生しない
- 「外部送信ゼロ」が技術的事実として説明でき、組織の導入審査で有利になる
- 一方で、端末故障やブラウザのサイトデータ削除による消失リスクが利用者に移るため、JSON エクスポート／インポートと未バックアップ警告が機能要件として必須になる
- 共有 PC での残留に対し、明示的な全データ削除と一時利用モードが必要になる
- Cloudflare Tunnel は使わない。配信するのは静的ファイルのみで、トンネルで繋ぐオリジンサーバーが存在しないため。Tunnel を挟むと自宅 PC の常時稼働が可用性の前提になり、かえって不利になる
- Cloudflare Access も使わない。特定の利用者に限定する仕組みであり、一般公開するアプリには適合しない

## ADR-002: サーバーサイドを導入する場合は TypeScript（Next.js / Node.js）を用いる

**状態**: 採用

**背景**

v2 系のサーバーサイドは PHP 8 + SQLite だった。ADR-001 によりサーバーは廃止したが、将来次のような要求が出た場合に再導入の可能性がある。

- 組織内での相関図の共有・共同編集
- 端末をまたぐ同期
- 監査ログを要件とする法人向け提供

**決定**

サーバーサイドを再導入する場合、実装言語は **TypeScript** とし、基盤は **Next.js または Node.js** を用いる。PHP は使用しない。

**理由**

- フロントエンドが TypeScript であり、`src/types.ts` の `ChartDetail` / `ChartNodeRecord` などの型定義と、`src/storage/validation.ts` のバリデーション規則をそのまま共有できる。v2 系では同じ規則を PHP と TypeScript で二重に持つ必要があり、`server/src/api_helpers.php` と UI の間で仕様がずれる余地があった
- `src/storage/` のリポジトリ層は `DocumentStore` インターフェースで抽象化済みのため、サーバー実装を足す場合も差し替え点は `src/api.ts` の 1 箇所で済む
- 言語を 1 つに保つことで、個人開発における保守対象を増やさない

**前提条件**

サーバーを再導入する時点で ADR-001 の前提が変わるため、次を再検討する。

- 要配慮個人情報を預かる場合の安全管理措置と漏えい時の対応体制
- 端末側での暗号化を前提とするゼロ知識構成にできないか
- 利用規約・プライバシーポリシーの全面改訂

## ADR-003: 保存順序と復元の整合性をストレージ層で保証する

**状態**: 採用

同居輪・同居文字を含む相関図は、共通の DocumentStore に保存する。一時利用モードでは同じ API をメモリストアへ接続する。旧 localStorage の同居情報は永続モードでのみ、対象のチャートを読み込む際に個別に移行し、書き込みに成功してから旧キーを削除する。移行済みの印を保存し、旧キーの削除に失敗しても新しいデータを上書きしない。

同じストアを使う API 呼び出しは共有キューで順序を保証する。ノード用 TanStack Query scope だけに更新の安全性を依存させない。対象は同一タブ内であり、複数タブ間の同時編集は保証しない。

編集画面は未保存変更と処理中の保存を待ってから書き出す。バックアップは全件を検証してから取り込み、置き換え復元は IndexedDB の単一トランザクションで実行する。失敗時は既存データを維持する。

ストアの初期化ではチャートの内容を検証しない。破損したチャートや移行元データがあっても、バックアップの検査・置き換え復元・全削除は実行できる。全件取得時の破損は黙って除外せず、エラーとして報告する。

編集画面のタイトルは入力世代を持ち、保存中に以前の値へ戻した操作も未保存の編集として扱う。保存状態とエラーは共通の Tracker が対象・変更項目・保存世代ごとに判定し、後続の保存が実際に反映した項目についてだけ古いエラーを解消する。出力前の待機は全処理が落ち着いてから未解決エラーを判定する。

ストレージ層の並列処理は、1件が失敗しても開始済みの全処理の終了を待ってから失敗を返す。移行や初期値保存を含む読み込みの残処理が、後続の復元・全削除と競合することを防ぐ。複数の処理が失敗した場合は入力順で最初のエラーを、その内容・コードを保持して通知する。

親1を削除して親2が残る場合は、親2を親1へ繰り上げる。過去の不具合による「親1なし・有効な親2あり」のドキュメントも読み込み時に修復し、更新日時と未知フィールドを保持したまま保存する。旧バックアップにも同じ正規化を適用する。新規・更新入力の親2のみの指定や、重複・無効な参照は従来どおり拒否する。
